# Parsing a DNS name into a fixed-layout key

**Question.** A DNS question name is a run of `(length byte, that many characters)` pairs ending in a
zero byte. The NF keys a longest-prefix match on a fixed 65-byte form of it (`struct dns_name` in
`dpdk-nfs/lib/util/dns_hdr.h`: the label count, then the labels top-level first, each as its length
byte plus 15 characters zero-padded). A Tofino parser cannot extract "`len` bytes": it selects on
the length byte and extracts fixed-size headers. Which fixed headers, so that the data plane ends up
with exactly the NF's bytes and bf-p4c accepts the result?

Variants, generated by `gen.py` (`python3 gen.py` writes one `dns_<variant>.p4` each; 4 labels of up
to 15 bytes, a 2048-entry ternary table over the 65 key bytes, the label reversal by count in the
MAU; compiled with `bf-p4c --target tofino2 --arch t2na`, SDE 9.13.4):

- `per_byte`: fifteen 1-byte headers per label, `len = k` extracts the first `k`, so character `n`
  always sits in header `n` and the key copy depends on the count alone. Zeroes the 60 byte headers
  in the parser first.
- `per_len`: fifteen headers per label of 1..15 bytes, `len = k` extracts the `k`-byte one, so exactly
  one is valid; one ternary table per key position (60 entries, 60 actions) copies the valid one.
- `per_piece`: the expert's 1/2/4/8-byte pieces by the bits of `len`, and the same per-position
  fill tables copying the pieces' bytes into 65 zero-initialised key byte locals.
- `per_piece_staged`: as `per_piece`, but one table per (piece, position), so that no action writes
  a key word from two sources, with slice writes into 32/32/32/24-bit key words.
- `per_piece_reversed`: the pieces kept whole; the key is count + per position (len, c1, c2, c4,
  c8), filled by a count-keyed 4-action table; the ternary table matches that layout.

**Result.**

| variant | bf-p4c | why |
|---|---|---|
| `per_byte` | PHV allocation fails | 60 deparsed 1-byte headers, each needing an 8-bit container of its own (`exact_containers`); the ordinary 8-bit sets B0-47 hit 100 % |
| `per_len` | PHV allocation fails | the odd-sized headers' tails need 8-bit containers the same way |
| `per_piece` | PHV allocation fails | with the B/H/W sets nearly empty: a deparsed field read at byte offsets is sliced into bytes (`diagnose_slicing found a unallocable slice: hdr.l0_c4.v ... [8:15]`), and 4×15 piece bytes + 5 length bytes = 65 one-byte containers, more than the 48 + 16 mocha Tofino 2 has |
| `per_piece_staged` | PHV allocation fails | same slicing, so staging the writes changes nothing |
| `per_piece_reversed` | compiles, 3 stages | 8-bit containers used: 9 B + 12 MB; 16-bit: 4; 32-bit: 13; the 65-byte ternary key spans 2 stages |

**Takeaways.**

- The label bytes cannot be touched individually in the MAU: every byte-granular access to a
  deparsed field turns into an 8-bit container, and the name alone needs more of those than the
  chip has. Only whole-piece (8/16/32/64-bit) moves are affordable, whatever the staging.
- So the NF's contiguous key layout cannot be assembled on the data plane. What can is the label
  order (a count-keyed copy of whole pieces). The table's key is therefore the *piece* layout of
  the NF's key -- count, then per position the length byte and the four pieces -- and whoever
  writes the entries has to lay the NF's prefixes out that way: split each label's 15 bytes into
  the pieces its length byte selects, and leave the pieces it does not select unmatched. A
  wildcard label is unmatched altogether, so no zeroing of unextracted pieces is needed.

## The CNAME's rdata (`varbit_rdata.p4`)

**Question.** The expert steps over a CNAME record's rdata with `pkt.advance`, so the deparser drops
those bytes and a punted response reaches the controller shorter than it was. Can the rdata be
carried through intact as a `varbit` header sized by `rd_length`?

**Result.** bf-p4c 9.13.4 never finished: `p4c-barefoot` was still running after 2 h 16 min at 4 GB
(killed). A length-driven varbit is expanded into one parser state per possible length, and 256 of
them is beyond it.

**Takeaway.** The bytes a parser skips are gone; a controller that re-reads the punted packet must
not rely on them. What the data plane parsed past the skip (the address, whether one was found)
travels with the packet instead.
